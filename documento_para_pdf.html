Este documento contiene el texto para diez diapositivas y un guion oral. Copia en tus diapositivas solo el bloque Texto para la diapositiva. El bloque Qué decir te ayuda a preparar la explicación. El bloque Qué mostrar indica el apoyo visual o la acción en el panel.

1. Contexto del proyecto

Al abrir una página, el navegador envía una solicitud HTTP a un servidor. El servidor recibe la petición y decide cómo responder. Esa comunicación también puede revelar información innecesaria o recibir demasiadas solicitudes en poco tiempo.

En este laboratorio configuramos Nginx para aplicar reglas de seguridad. Nginx oculta su número de versión, envía cabeceras de seguridad, restringe los métodos permitidos y limita el tráfico por dirección IP. Docker permite ejecutar el entorno de forma reproducible.

La página inicial se convirtió en un panel interactivo. Ahora podemos enviar solicitudes desde el navegador y observar las respuestas del servidor. La protección está en Nginx. El panel permite probarla y explicarla con evidencia visible.

Objetivo general: demostrar, en un entorno local, cómo una configuración de Nginx reduce información expuesta y controla solicitudes HTTP mediante pruebas observables desde un panel web.

Conceptos que conviene entender

Concepto Explicación sencilla
Nginx El servidor web que recibe las peticiones y aplica las reglas.
HTTP La forma de comunicación que usamos entre navegador y servidor.

Diapositiva 5. Hardening del servidor

Texto para la diapositiva

  • Ocultamos el número de versión de Nginx.
  • Añadimos cabeceras con instrucciones de seguridad para el navegador.
  • Permitimos GET y HEAD en la ruta del panel.
  • Referencia académica: OWASP A05:2021, configuración de seguridad incorrecta.

Qué decir

Hardening significa ajustar la configuración para reducir riesgos. Aquí el servidor informa que usa Nginx, pero no muestra su número de versión. También envía cabeceras que restringen recursos y la inclusión de la página en otros sitios. Como este laboratorio sirve contenido de consulta, permitimos GET y HEAD. Estas medidas se relacionan con la categoría de configuración de seguridad incorrecta de OWASP 2021.

Qué mostrar

La tabla de cabeceras del panel después de ejecutar GET. Señala Server: nginx, X-Frame-Options: SAMEORIGIN y Content-Security-Policy.

Diapositiva 6. Control del ritmo de solicitudes

Texto para la diapositiva

  • Tasa configurada: 5 solicitudes por segundo por IP.
  • burst=10: tolerancia adicional a una ráfaga breve.
  • nodelay: atención inmediata dentro de esa tolerancia.
  • Código configurado para el rechazo: 503.

Qué decir

El limitador lleva una cuenta por dirección IP. La tasa es de cinco solicitudes por segundo y existe una tolerancia adicional para picos breves. Con nodelay, las solicitudes admitidas dentro de esa tolerancia pasan sin una espera añadida por el limitador. Cuando el exceso supera lo permitido, Nginx lo rechaza. Por eso no debemos interpretar la regla como un máximo rígido de cinco respuestas en cualquier segundo.

Qué mostrar

Los valores de configuración que aparecen arriba de las pruebas. Si deseas mostrar código, basta con estas dos líneas de nginx.conf:

limit_req_zone $binary_remote_addr zone=zona_limite:10m rate=5r/s;
limit_req zone=zona_limite burst=10 nodelay;

Diapositiva 7. Prueba de una consulta normal

Texto para la diapositiva

  • Acción: pulsar «Probar consulta GET».
  • Respuesta esperada: 200 OK.
  • Evidencia: código HTTP, tiempo y cabeceras recibidas.

Qué decir

Primero enviamos una consulta normal. El panel hace una petición GET real a Nginx. Si la solicitud está permitida y hay cuota disponible, recibimos 200 OK. Debajo podemos leer las cabeceras de esa respuesta. Esto muestra tanto el acceso al contenido como las instrucciones de seguridad que el servidor entrega al navegador.

Qué mostrar

Cambia al navegador, pulsa el botón GET y señala el resultado. Baja a la tabla de cabeceras. El estado «7 de 7» indica cuántas cabeceras de la lista se recibieron, no una certificación de seguridad.

Diapositiva 8. Prueba de un método restringido

Texto para la diapositiva

  • Acción: pulsar «Probar bloqueo de POST».
  • El panel envía un POST vacío.
  • Respuesta esperada: 403 Forbidden.
  • Nginx aplica la restricción en el servidor.

Qué decir

Ahora enviamos un POST sin datos. Aunque el navegador puede hacer esa solicitud, Nginx la rechaza porque la ruta solo permite GET y HEAD. El resultado esperado es 403 Forbidden. Con esta prueba comprobamos una política del servidor. En una aplicación que necesitara formularios o una API, habría que permitir los métodos adecuados en las rutas correspondientes.

Qué mostrar

Pulsa POST y muestra el 403 en el resultado y en el registro. Explica que esta prueba comprueba el método permitido, sin realizar cambios en datos.

Diapositiva 9. Prueba de una ráfaga

Texto para la diapositiva

  • Acción: pulsar «Enviar ráfaga de 40».
  • Hasta 6 peticiones simultáneas desde el navegador.
  • El panel cuenta las respuestas permitidas y rechazadas.
  • Ejemplo observado: 11 respuestas 200 y 29 respuestas 503.

Qué decir

Enviamos cuarenta solicitudes para superar la tasa permitida en un intervalo corto. En una ejecución del panel observamos once respuestas permitidas y veintinueve rechazos con código 503. Es un ejemplo de esa prueba y las cantidades pueden cambiar. Lo que debemos analizar es si el servidor aplicó el límite. En los registros de esa ejecución apareció limiting requests, que confirmó el rechazo por tasa.

Qué mostrar

Pulsa la ráfaga y señala la barra, los contadores y la vista de la respuesta 503. Abre «Registro de solicitudes». Usa las cantidades que aparezcan en vivo. Si el envío fue más lento y no hubo 503, muestra ese resultado y explica que quizá no se superó la tasa.

Nota para la diapositiva: si incluyes 11 y 29, acompáñalos con «Ejemplo de una ejecución local». No representan una tasa de eficacia contra ataques reales.

Abre http://localhost y recarga con Ctrl + F5 si tenías una versión anterior. La demostración de los botones no requiere instalar herramientas dentro del contenedor cliente.

Durante la exposición

Paso Acción Idea para explicar
1 Señalar el diagrama del panel. El navegador pide contenido y Nginx aplica sus políticas.
2 Ejecutar GET. Una consulta permitida devuelve 200. Las cabeceras también vienen del servidor.
3 Ejecutar POST. La política de métodos rechaza esta solicitud con 403.
4 Ejecutar la ráfaga de 40. El ritmo excesivo puede producir rechazos 503. Mostrar los valores recibidos.
5 Abrir el registro de solicitudes. Cada fila corresponde a una petición de la última prueba.

El panel espera tres segundos entre pruebas. Esto da tiempo para recuperar la cuota si no hay otro tráfico de la misma IP. Varias pestañas pueden compartirla. El panel mide sus propias solicitudes, no todo el tráfico del servidor.

Si necesitas confirmar la causa de los rechazos, usa este único comando de apoyo:

docker logs --tail 30 servidor-defensa

La expresión limiting requests asociada a las solicitudes de la prueba indica que actuó el límite de tasa. La configuración también utiliza 503 para el límite de conexiones, por lo que el código por sí solo no distingue las dos causas.

Si la presentación debe durar cinco minutos, explica brevemente el problema y la arquitectura, realiza las tres pruebas y cierra con los resultados. Las diapositivas sirven de apoyo.

6. Apoyo técnico para preguntas

Significado de las cabeceras

Cabecera Función que puedes explicar
Server: nginx Identifica el servidor sin mostrar su número de versión.
X-Frame-Options: SAMEORIGIN Restringe la inclusión de la página en marcos de otros orígenes.
X-Content-Type-Options: nosniff Restringe la interpretación de contenido de forma distinta al tipo declarado.
Content-Security-Policy Define orígenes y recursos permitidos para la página.
Referrer-Policy Controla qué información de procedencia se envía al navegar o pedir recursos.
Permissions-Policy Deshabilita ubicación, cámara y micrófono para esta página.
X-XSS-Protection: 0 Desactiva un filtro XSS antiguo. La configuración utiliza CSP como medida complementaria frente a ciertos riesgos del navegador.

Las cabeceras usan always, que permite añadirlas también en las respuestas de error de esta configuración. Recibirlas demuestra su presencia. Evaluar su eficacia frente a cada ataque exigiría pruebas específicas.

Controles adicionales del archivo nginx.conf

  • limit_conn zona_conn 20: limita por IP las conexiones que el módulo contabiliza. Nginx las cuenta cuando procesa una solicitud y ya leyó la cabecera completa. No equivale a contar todos los sockets TCP abiertos.
  • client_header_timeout 10s: limita la espera para leer la cabecera.
  • client_body_timeout 10s: limita la espera entre lecturas sucesivas del cuerpo.
  • send_timeout 10s: limita la espera entre escrituras sucesivas hacia el cliente.
  • keepalive_timeout 15s: limita cuánto tiempo permanece ociosa una conexión reutilizable.
  • client_max_body_size 1m: limita el tamaño del cuerpo admitido.
  • Los montajes :ro permiten leer los archivos del proyecto desde el contenedor sin modificarlos mediante esos montajes. No convierten todo el sistema de archivos del contenedor en inmutable.

Estos ajustes complementan las pruebas principales. No es necesario leerlos todos durante la exposición.

Preguntas frecuentes y respuestas sencillas

¿Por qué una página sencilla sirve para un proyecto de seguridad?

Porque las reglas se aplican en Nginx antes de entregar el contenido. El panel envía peticiones y presenta evidencia de esas reglas. La complejidad de la página no determina si el servidor aplica controles.

¿Los números del panel son simulados?

Los resultados se calculan con las respuestas de las peticiones reales de la última prueba. Los valores de configuración que aparecen arriba, como 5 solicitudes por segundo, son textos que representan nginx.conf. El panel no descubre automáticamente los cambios de configuración.

¿Un 503 significa que el servidor se cayó?

503 significa que la solicitud no pudo atenderse en ese momento. En nuestra prueba los registros mostraron un rechazo por tasa. En otros contextos puede tener otras causas.

¿Por qué pasan más de cinco solicitudes?

Porque existe una tolerancia de ráfaga y el límite se recupera con el tiempo. También influye la cuota consumida antes de la prueba. Por eso las cantidades varían.

¿La regla distingue usuarios legítimos de atacantes?

La regla aplica una cuota por IP. No determina la intención de quien envía la petición. Clientes que comparten una IP también pueden compartir el límite.

¿Qué relación tiene con OWASP?

Usamos A05:2021 como referencia de configuración de seguridad incorrecta. Las cabeceras y la reducción de exposición son medidas relacionadas con esa categoría. El laboratorio no representa una auditoría de todo OWASP Top 10.

¿Por qué usan Docker?

Para preparar el entorno con una configuración repetible y separar los componentes en contenedores. El puerto publicado permite acceder al servidor desde el equipo.

¿Por qué 503 y no 429?

Este proyecto configura 503 como respuesta de los limitadores. 429 es el código específico para exceso de solicitudes y sería una opción si se ajustara la política y su página de error.

¿Tienen protección completa contra Slowloris o DDoS?

Hay controles de tiempo y conexiones configurados. Para evaluar esos ataques necesitaríamos pruebas diferentes. Lo demostrado aquí es el comportamiento HTTP local de las pruebas realizadas.

¿Ocultar la versión elimina vulnerabilidades?

Reduce información expuesta. Las actualizaciones y la revisión de la configuración siguen siendo necesarias.
